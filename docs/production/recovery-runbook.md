# 恢复与升级操作

范围：Go 1.25+ 源码构建；Windows x64/Linux 本地 CLI。测试覆盖的是完整恢复日志已写入且文件系统仍可用时的应用进程崩溃/强退回滚；这不证明断电、控制器/磁盘缓存丢失、文件系统损坏或恢复介质故障时可恢复。

## 升级
1. 停止所有旧版 CLI、后台分析进程和编辑器扩展进程，再替换二进制；禁止混用旧 O_EXCL 锁协议与新 OS 锁协议。
2. 备份本机私有状态目录，禁止把源码快照/恢复日志提交到 Git 或发到公共问题中。
3. 打开项目并查看 status 的 diagnostics。旧 `.lock` 文件可保留；新锁不会因磁盘文件存在而永远阻塞。不要在运行期间删除锁文件，否则会破坏互斥。

## 坏记录
坏历史 JSON 移到项目私有状态中的 quarantine，默认 0700 目录/0600 文件（Windows 权限仍受用户配置目录 ACL 约束）。隔离内容不参与 UI、共享或模型材料。诊断仅包含文件名与计数，不包含原文。

排除规则变化后，无法安全解析的隔离原文会清除，不能用于恢复被撤销的内容。先评估是否仍获准保留，再人工备份；不要把隔离记录直接移回活动命名空间。丢失或损坏的活动基线不能伪造恢复，开始新的轮次前应查看 diagnostics。

settings.json、usage.json 损坏时保留原文件并失败关闭，不自动重置授权或清空用量。按受信任备份及服务商实际用量修复；禁止以删除 usage.json 作为恢复预算的方法。本地单条读取上限 256 MiB，为 JSON 转义的 before/after 快照保留空间；超过范围的历史记录需人工检查与拆分/归档。

## 应用日志
apply-journal.json 在任何源码替换前写入，包含完整 before/after 和事务标识。必须视为源码敏感数据。新应用请求只允许一个源码文件；历史版本留下的多文件日志仍可能需要恢复。源码暂存文件路径由日志预先记录的事务 ID 推导；崩溃重开会清理暂存并尝试回滚已应用内容。

如果出现“外部修改”或“排除规则变化”：

1. 停止并发编辑、格式化器及其他工具写入，保留当前文件和日志。
2. 在本机比较日志 before/after 与当前文件，人工确认每个文件应保留的版本。不要上传含源码的日志。
3. 只有全部文件状态明确后才人工完成恢复，并备份后移出日志；不要先删除日志强行继续。

工具锁只协调本工具；比较到替换之间没有跨工具 CAS。请在应用期间暂停并发编辑。新多文件 apply 会在写 journal 或源码前拒绝；单文件使用暂存文件与替换操作，但 rename 和同步调用不构成断电或介质损坏恢复保证。若恢复旧版本多文件 journal，进程崩溃后仍可能短暂暴露部分状态；恢复仅是应用级回滚，不是文件系统原子事务。Windows 上也不承诺所有文件系统的突然断电原子性。

## 发行验证边界
CI 生成候选包并检查文件/源码清单一致性，另验证修改 core.js 未更新清单、删除清单两种损坏被拒绝。这不是任意恶意 VSIX 的签名认证或独立来源证明。公开发行仍需正式 publisher、许可证和明确发布操作，CI 不执行发布。
